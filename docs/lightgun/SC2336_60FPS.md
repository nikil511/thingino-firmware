# SC2336 720p60 (Phase 3)

Status: **validated on hardware [HW]**. It holds a genuine 60.0 fps over 10,000 frames.

## Source

`espressif/esp-video-components`, file
`esp_cam_sensor/sensors/sc2336/private_include/sc2336_mipi_2lane_24Minput_1280x720_raw10_60fps.h`,
Apache-2.0. The SC2336 chip ID (0xCB3A) matches the Sonoff sensor and the
Ingenic `t23/sc2336.c` driver.

## Timing **[SRC]**

| | stock 1080p (mode 0) | 720p60 (mode 1) |
|---|---|---|
| MCLK / MIPI | 24 MHz, 2 × 405 Mbps RAW10 | same |
| PLL regs 0x36e9-0x36ed, 0x37f9-0x37fd | 09 0c 1c 28 / 09 32 11 37, final 0x53/0x53 | identical |
| Pixel clock | 81 MHz | 81 MHz |
| HTS (0x320c) | 2250 | 1800 |
| VTS (0x320e) | 1440 (25 fps), 1200 (30 fps) | 750 |
| fps = 81e6 / (HTS × VTS) | 25.0 / 30.0 | **60.0** |
| Line time | 27.8 µs | 22.2 µs |
| Array window | full (1928 × 1088) | x 308..1619, y 180..907 (1312 × 728) |
| Output | 1920 × 1080 | 1280 × 720, offset (16, 4) |
| Max exposure | VTS−6 lines (stock driver: VTS−4, which stretches frames) | VTS−6 = 744 lines = 16.5 ms |
| Other diffs | — | 0x301f 02→30, 0x3395 ff→30, +0x3641=03 |

The 720p mode is a **centre crop**: 2/3 of the field of view in each
direction. It is not binned. The extra speed comes from fewer rows (VTS 1440
→ 750) and a shorter line (HTS 2250 → 1800).

**[CALC]** MIPI load: 1280 × 10 bit ÷ 810 Mbps = 15.8 µs per line, inside the
22.2 µs line time (71%). The stock 1080p mode uses 23.7 / 27.8 µs (85%).

## Driver changes (`package/ingenic-sdk/0004-sensor-t23-sc2336-selectable-modes.patch`)

- `sensor_mode` module parameter, plus a `sensor_modes[]` table holding
  size, HTS, default VTS, minimum VTS, max fps, exposure margin and pixel clock
  for each mode.
- `sensor_apply_mode()` runs before `sensor_common_init()`. It sets
  `/proc/jz/sensor/{width,height,max_fps}`, `mipi.image_twidth/theight`,
  `total_width/height`, the integration-time limits and `one_line_expr_in_us`.
- `set_fps` uses the mode's max fps and pixel clock. It rejects any request
  that would need a VTS below the mode's minimum (active rows + 8) instead of
  writing an impossible frame length.
- Mode 0 still writes the original 1080p table byte for byte.

To select a mode: put `sensor_sc2336_t23 sensor_mode=1` in
`/etc/modules.d/30-sensor` and reboot.

## Validation plan

```sh
echo "sensor_sc2336_t23 sensor_mode=1" > /etc/modules.d/30-sensor; reboot
dmesg | grep sc2336                 # "mode 1: 1280x720 hts 1800 vts 750 max 60 fps"
FPS_LIST="50 60" EXPO=300 lgbench   # 50 and 60 fps, native + 640x360 + 320x180
```

To pass, 60 fps needs all of:

- a median `ts` interval of 16.67 ms ± 0.1
- a p99 interval under 17.5 ms
- zero duplicate timestamps and zero identical-content frames over 10,000 frames
- delivered fps equal to ISP fps when there's no workload

Use a fixed exposure (`EXPO`, in lines, at most 744). Otherwise auto
exposure in dim light may lengthen the frame.

## Results **[HW]**

Mode 1, auto exposure, indoor scene. Nothing changed in the camera's flash:
the module is loaded at runtime (see [CAPTURE_BENCHMARK.md](CAPTURE_BENCHMARK.md)).
dmesg confirms the mode: `sc2336 mode 1: 1280x720 hts 1800 vts 750 max 60 fps`.

| Config | ISP fps | Delivered | Median / p95 / p99 interval | Drops / dup ts / repeated | ISP→app p50 | CPU sys / lgcap |
|---|---|---|---|---|---|---|
| 1280×720 @50 | 50.0 | 50.01 | 20.00 ms | 0 / 0 / 0 | 3.18 ms | 13.4% / 10.1% |
| 1280×720 @60 | 60.0 | 60.00 | **16.667 / 16.681 / 16.730 ms** | 0 / 0 / 0 | 3.51 ms | 25.6% / 13.6% |
| 720p60 → 640×360 | 60.0 | 60.01 | 16.667 ms | 0 / 0 / 0 | 0.81 ms | 22.8% / 4.9% |
| 720p60 → 320×184 | 60.0 | 60.01 | 16.667 ms | 0 / 0 / 0 | 0.48 ms | 10.5% / 2.9% |
| 720p60 → 640×360, `-w 1`, 10,000 frames | 60.0 | 59.98 | 16.667 ms | 3 / 0 / 0 | 2.28 ms (p99 3.09) | 38.2% / 23.5% |
| 720p60 → 320×184, `-w 1` | 60.0 | 60.00 | 16.667 ms | 0 / 0 / 0 | 0.48 ms | 24.1% / 7.6% |

**It passes every criterion:**

- a median interval of exactly 16.667 ms
- p99 under 17.5 ms
- zero duplicate timestamps and zero repeated-content frames in every run
- delivered fps equal to ISP fps

The 3 drops in the 10,000-frame tracking run came from rare 13–17 ms workload
spikes (p99 is 3.9 ms). They weren't caused by the sensor or the ISP: the
no-workload runs dropped nothing.

Unlike mode 0, this mode lands exactly on nominal (60.00, not 59.7). So the
small mode 0 shortfall isn't a pixel-clock error that affects all modes.

FOV: mode 1 is the centre 2/3 × 2/3 of the 1080p frame **[SRC]**. Frame
comparisons are in [FOV_COMPARISON.md](FOV_COMPARISON.md).
